# 端口、绑定与端口信号

> 本文档定义节点端口的两类绑定语义,以及控制整个网络通断的**端口信号**——每个数据端口自带的电平。
> 相关文档:[图运行时总纲](./graph-runtime-overview.md) · [执行模型](./graph-execution-model.md) · [节点类型](./graph-node-types.md) · 应用模式与场景图式(eidolon-runtime 仓库 docs/graph-application-patterns.md)

## 1. 核心命题

> **连线 = 数据流动与触发方向(推);内嵌绑定 = 执行时读取的对象(拉);端口信号 = 每个端口自带的电平,决定这个端口是否带电(参与传播)。三种机制,不互相污染。**

## 2. 端口双绑定模型

端口除了连线,还有**内嵌绑定**——声明在接口上、编辑器可见,但不构成"流":

| 端口 | 绑定种类 | 语义 |
|------|---------|------|
| 输入 | 连线 | 参与触发等待;上游输出满足/唤醒该端口 |
| 输入 | 默认常量 | 即时满足,值为常量;不参与触发等待 |
| 输入 | 全局读取 | 即时满足,**执行时取全局变量最新值**;不参与触发等待 |
| 输入 | 可选参数 | 可不连线(裸端口校验豁免);不接线/信号禁用 → 回退配置默认值;接线即参数参与触发 |
| 触发输入(TriggerIn) | — | **函数调用入口**:到达即请求一次 activation;数据线(载荷)或信号线(电平变化)均可激活;无绑定/optional/信号槽 |
| 输出 | 连线 | 执行时产出即投递,推给下游 |
| 输出 | 全局写入 | 执行时写入命名的全局变量 |

本节描述**数据端口与触发端口**;端口信号与门控见 §4。

**输入组 = 函数**:inputs = 参数(数据端口),triggers = 调用入口(TriggerIn);
端口信号 = 该参数是否使用默认值(信号禁用 → 回退配置默认,即使有连线数据);
只有全部参数被禁用,对应输出端口才自动禁用(自动传导)。
必需参数被关闭 → 组不执行。

**组触发策略**(`InputGroup.policy`):策略描述"如何产生 activation",不描述执行逻辑:

| 策略 | 触发条件 | 适用 |
|------|---------|------|
| `ON_ALL_DATA_READY`(默认) | 组内**有效**(未关闭)的连线数据输入全部有新值 | 组合节点(Join 类),现状行为 |
| `ON_ANY_DATA` | 任一有效连线数据输入有新值 | 任一到达即处理 |
| `ON_TRIGGER` | 任一 TriggerIn 收到激活请求 | 纯事件节点(Buffer.flush、LlmCall._result) |
| `ON_DATA_AND_TRIGGER` | 数据齐 + 激活请求(先到者等待) | 显式门控执行(Timer.arm) |

常量/全局读取绑定端口不参与触发,值随读随用;可选参数未接线时不参与触发。

**触发端口(TriggerIn,1.0 独立端口)**:**函数调用级**——数据线到达 = 载荷 + 激活
请求,信号线电平变化 = 激活请求(双沿都触发,电平保持不重复)。触发事件与数据
fresh 同构:组触发后消费清空,未触发保留(等齐语义);端口信号关闭时事件一并失效。
Trigger 是消费语义不是数据类型——Data 与 Signal 在激活层汇合,但不互通
(信号线连数据端口仍被拒绝,见 [触发语义设计](./graph-trigger-semantics.md) §2)。
`DataIn.trigger=True` 旧标记已随 1.0 移除(旧资产拒绝加载)。

无连线、无默认、无引用的**裸数据端口** → 编辑事务校验报错(强迫显式;可显式声明默认 None);
裸 TriggerIn 合法(没有显式触发源 = 仅依赖数据策略激活)。

**瞬态与持久**:连线输入是**瞬态事件**(触发后缓冲清零);常量/全局读取绑定是**持久输入**(不参与触发、不消费)。需要"配置一直有效"就用绑定——不需要给端口增加消费策略这类新机制,绑定种类已经把两类输入区分开了。

## 3. 为什么全局变量不是输出源

全局变量是**状态**,不是输出。它被读取时不产生输出、不唤醒下游:

- 全局被改 → 没有任何节点被触发;
- 读取它的节点在**下一次因其他原因执行时**才看到新值;
- 读取是拉,不是推——全局写入不进入传播,不会产生输入污染。

## 4. 端口信号:数据与信号每端口成对

> **每个数据输入/输出端口都自带一个信号(电平),信号数量 = 数据端口数量。信号回答"这个端口现在带电吗":带电的端口参与传播与等待,断电的端口视为不存在。**

| | 数据 | 信号 |
|---|---|---|
| 载体 | 端口的缓冲/值 | 依附在端口上的电平 |
| 语义 | 世界内容 | 端口是否带电 |
| 输入 | 一格缓冲,新值覆盖 | active = 有效;inactive = 关闭(不存在) |
| 输出 | 执行产出即投递 | 自动联动(见 4.1) |

### 4.1 输出信号:数据节点唯一逻辑 + 信号节点

**数据节点**(不声明控制输出端口的节点)的信号行为只有一条规则,**实现永远不触碰信号**:

> 输出组的**对应输入组**(声明一一对应)的信号**全部关闭** → 该组输出信号输出**关闭**;组内至少一个输入信号 active → 输出信号保持 active。节点被门控或熔断 → 全部输出信号输出关闭。

推论:

- 关闭信号沿连线流向下游:下游对应输入信号随之关闭 → **下游不会等待一个永远不会到来的输出**。整段链自动"熄火",上游恢复后自动"复电"——结构级门控不需要给每个节点拉控制线。就像 if-else 里条件永不满足的分支:整条链路永远不带电;
- 等待输入中的节点:输入信号 active → 输出信号保持 active → 下游照常等待(规则自然给出,无需特判);
- 执行时某输出未写数据 → 只影响是否投递值,不影响信号;
- 数据节点输出信号的**电平**只有自动传导这一个来源(实现永不写信号),但输出
  **信号端口可显式拉线**到任何信号接收端(控制输入 / 数据输入的信号槽)——拉线
  不改变电平,只是显式路由;不拉线则沿数据线自动传导;
- 端口重新开启时缓冲为空(关闭期间的旧值丢弃),等待新值。

**信号节点**(声明控制输出端口的节点)是信号逻辑的唯一所在地:读输入信号、写输出信号(未写保持原电平),**可以接受数据**(数据输入作为条件),让信号的逻辑在图中被显式表达。数据节点永远不写信号。

### 4.2 输入信号:显式屏蔽 + 自动传播

1. **显式信号线**:信号源(控制输出,或数据输出的信号端口)连到本输入信号上——
   单个输入信号屏蔽 / 显式路由;
2. **自动传播**:上游输出信号 inactive → 本输入信号自动 inactive;
3. 默认 active:不连线即带电。

**以信号线为准**:端口接入了显式信号线 → 信号电平以信号线为准(自动传导不生效);未接入 → 自动传导。

**扇入禁止**:每个输入端口至多一条数据线、至多一条信号线——一个输出可以分发到多个输入,一个输入不可接受多个来源;多个来源的组合**必须显式使用信号节点**(如两个信号取 AND 输出),不允许隐式多源。

### 4.3 控制端口:enable 与 level

控制端口继续承载两类职责(它们同样是信号,只是不依附于数据端口):

| 声明 | 语义 |
|------|------|
| control-in:门控(enable) | active = 门开;inactive = 不执行 → 输出信号自动关闭并传播(4.1) |
| control-in:电平(level) | 纯电平输入,引擎不介入——AND / OR / NOT / Latch / Timer 等逻辑元件的组合线 |
| control-out | 电平输出:既可连其他控制端口(逻辑链),也可连**数据端口的信号**(显式屏蔽) |

- 逻辑元件(AND/OR/NOT/比较器/开关)是普通节点类型资产,它们的输入输出本身就是信号;
- **数据节点唯一可声明的控制端口是 enable**(引擎级门控);声明了控制输出端口的节点即信号节点(4.1);
- 控制输出连到数据端口信号的连线在交叉连线校验中放行(这是唯一合法的跨通道连线)。

### 4.4 默认电平与保持

- 端口信号默认 active(带电);
- 控制端口的默认电平由声明决定(缺省:门控 = 常开,电平 = inactive);
- 电平永远有定义、采样保持,按状态持久化(见 [持久化与编辑](./graph-persistence-and-editing.md));
- 信号不参与触发判定——它是"端口是否有效"的开关,不是触发器。

### 4.5 边界情况

- **全部数据输入被关闭** → 节点不执行,输出信号按默认传导输出关闭并传播(4.1);
- **关闭 ≠ 发 None**:关闭的端口不投递事件、不参与计算;None 是节点主动发的一个值,是一次真实的事件投递;
- 等待中的节点输出信号保持 active:下游照常等待;真正"永远不会来"的输出(门控/全屏蔽)才会让下游断电;
- 关闭期间缓冲失效;重新开启时缓冲为空,等待新值。

### 4.6 缺氧式离散信号网络

端口信号网络的灵感是《缺氧》自动化系统:**离散信号网络**——机器自己知道什么时候该输出信号,接收端只需要知道"收到信号后做什么",复杂的自动化逻辑不是写进中央控制器,而是由机器 + 导线 + 信号组合出来。现在这个类比是字面意义的:**信号 = 电,端口信号决定哪条导线带电**。

- **输出信号**:节点"不可能产出"时自动断电(4.1);满足什么条件属于节点自己的实现;
- **输入信号**:带电 = 参与,断电 = 不存在,全系统一致;
- 一个节点天然是一个自动化元件:`[比较器]` 数据入、信号出;`[开关]` 玩家操作入、信号出;`[计时器]` 状态变化出信号;`[战斗系统]` 只暴露数据输入与信号。

### 4.7 基础元件是节点类型资产,不是引擎机制

自动化能力不是引擎写死的,而是由基础元件组合出来的。以下全部是**普通节点类型资产**,运行时对它们零特殊处理:

```
Clock(时钟)  Comparator(比较器)  AND  OR  NOT  Latch(锁存器)
Switch(开关)  Counter(计数器)  Timer(计时器)  Threshold(阈值)  Random(随机)
```

例:温度超过 30℃ 且玩家进入房间时启动空调:

```
[世界温度] → [温度比较器] ──信号──┐
                                  ↓
[玩家位置] → [房间判断器] ──信号── [AND] ──信号──→ [空调]
```

用户同样可以自制 `[剧情条件判断器]` `[任务完成判断器]` `[世界切换判断器]`——对运行时没有区别。**用户编辑的不是"程序",而是在搭建一个可以运行的世界自动化网络。**

### 4.8 数据网络与信号网络的对偶

图中存在两种流,在节点内部交汇:

```
                数据网络:  世界状态 ─────→ 节点 ─────→ 世界状态
                信号网络:  通断    ─────→ 节点 ─────→ 通断

        data ────────────────→│            │───→ data
                              │    NODE    │
        signal ──────────────→│            │───→ signal
```

- **数据流回答**:"世界中有什么、发生了什么、状态是什么。"
- **信号流回答**:"网络的哪些部分现在带电、哪些计算现在被允许发生。"
- 数据→信号(比较器)、信号→数据(条件选择)的转换必须经节点内部,端口层不混——但信号依附在每个数据端口上,这是网络的控制面。

### 4.9 结构级门控:整段子系统的计算许可

端口信号最大的价值是**结构级门控(computation gating)**——不必让一段子系统里的每个节点每 epoch 自问"现在是不是战斗?",而是在入口处明确告诉它:**这一整段系统现在没有运行资格**。

```
剧情状态 → [条件节点] ──信号──→ [战斗系统]
                                     │
                                     ├→ [战斗状态] → [敌人 AI] → [行为规划]
                                     └→ [LLM] → [动作生成] → [世界状态更新]
```

`enable = inactive` 在节点实现**之前**被运行时拦截:节点不执行、内部状态不更新,**输出信号自动关闭并沿连线向下游传播**——整段子系统自动熄火,不需要给每个节点拉控制线(见 [执行模型](./graph-execution-model.md) §3)。对 LLM 节点这意味着**不进入 prompt 构建、不进入 API 调用、不产生 token**——这不仅是语义上的关闭,也是实际的成本门控。

### 4.10 V1 语义收敛

V1 严格控制信号语义:

```
control-in
    ├── enable(门控整节点)
    └── level(逻辑组合线)

数据端口的屏蔽 = 端口信号内建承载(不再需要 mask 声明)
```

**不**引入 pause / cancel / reset / flush / priority / interrupt / force / abort 等——它们很容易把控制信号逐渐变成第二套事件系统。原则:

> **数据负责传递世界内容,信号负责决定网络是否带电。**

### 4.11 反模式:数据伪装成控制

不用端口信号、改在数据里塞 `{enabled: false, payload: ...}`,会让每个节点都出现 `if not input.enabled: return`——**控制逻辑重新隐藏进节点内部**,与"一切显式"原则冲突。有了每个端口自带的信号,图的视觉结构本身就表达"数据从哪里来,以及这段网络什么时候带电",用户不需要读代码就能理解整个世界何时运行什么系统。

**世界语义与计算语义的边界**,最终归结为:

- `data: world.reality = MEAT`(世界现在是不是血肉世界)→ 数据,可以被任何节点读取;
- `signal: meat_chain = active`(血肉世界相关计算现在是否运行)→ 信号,只决定网络通断;

两者即使最终都表现为 `true / false`,也不能因此合并。

## 5. 可编排的控制模式

- 旁路某段数据处理:屏蔽其输入端口信号,节点按部分数据工作;
- 暂停一条链:屏蔽链上某输出端口信号,下游断电并冻结;
- 给反馈环调速:用方波信号周期性屏蔽反馈边;
- 章节门控:按剧情状态启用/关闭整段子系统(战斗、解谜、特殊世界)——多个系统**同时存在于图中,只有带电的计算网络被启用**,而不是在程序里写 `if`(实例见 应用模式与场景图式(eidolon-runtime 仓库 docs/graph-application-patterns.md) §6 双世界)。

全部是连线,不是新原语。

## 6. 校验相关

- 端口绑定合法性:裸数据端口报错;绑定必须指向已声明资产;
- 连线 kind 匹配:data→data、信号→信号,交叉连线报错;信号线来源 = 控制输出或
  **数据输出的信号端口**(电平由自动传导决定,拉线只是显式路由/屏蔽);
- 扇入禁止:每个输入端口至多一条数据线、至多一条信号线(组合必须显式使用信号节点);
- 引用存在性:绑定引用的全局变量/常量必须已声明,否则提交校验抛异常(见 [资产系统](./graph-assets.md));
- 完整校验清单见 [持久化与编辑](./graph-persistence-and-editing.md) §5。
