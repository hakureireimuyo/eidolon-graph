# 节点类型:类式接口契约

> 本文档定义节点类型资产:**像类一样只定义接口,节点内部自维护数据和状态,对外暴露输入输出接口;内部是什么都没关系。**
> 相关文档:[图运行时总纲](./graph-runtime-overview.md) · [端口、绑定与控制信号](./graph-ports-bindings.md) · [资产系统](./graph-assets.md) · [节点协议(内核↔节点 ABI)](./node-protocol.md) · 人格、意图与认知链(eidolon-runtime 仓库 docs/graph-cognitive-chain.md)

## 1. 核心命题

> **节点类型 = 接口契约 + 实现绑定。接口声明是核,实现是黑盒;嵌套子图只要外部契约成立,就是一个节点。**

与 OOP 的类同构:类型定义(类)声明端口与字段;实例 = 类型 + 字段值覆盖 + 连线。更进一步:**输入组 = 方法,输出组 = 方法的返回值,状态字段 = 实例字段(方法间共享),配置字段 = 只读字段**——数据节点、信号节点、仅输入节点、仅输出节点等都是节点基类的派生形态,由声明决定。

节点概念与编程概念的强关联:

| 图概念 | 编程概念 |
|--------|---------|
| 节点实例 | 类实例 |
| 节点类型 | 类 |
| 输入组 | 方法(参数) |
| 输出组 | 方法返回值 |
| 初始化输入 | `__init__` 参数 |
| 状态字段 | 实例字段(方法间共享) |
| 配置字段 | 只读字段(构造时设定) |
| 连线 | 事件投递(调用方) |
| 资格计算(Readiness 判定 / pending 消费)/ 组缓冲 / 输出投递 / 状态提交 | **基类 final 方法,不可重载** |
| 各组处理逻辑 / 初始化逻辑 | 可重载方法(节点实现者编写) |

**基类边界**:资格计算(Readiness 判定、pending 消费)与输出投递属于基类的 final 方法,任何节点实现都不可触碰——这是"数据节点永远不触碰信号逻辑"的编程表述。用户节点类型只能重载两件事:各输入组的处理逻辑,与初始化逻辑;激活策略经声明(TriggerIn / policy)改变,不靠重载。

## 2. 声明骨架

| 声明部分 | 内容 |
|---------|------|
| 数据端口 | data-in / data-out;名称、类型注解(可选)、绑定默认(常量 / 全局读取 / 全局写入 / 无)、**资格槽(可选声明)**、**缓存策略(Replace 默认 / Append)** |
| 信号端口 | signal-in(节点级资格 enable / 端口级资格槽)与 signal-out(**仅信号节点声明**);名称、默认电平 |
| 状态字段 | 名称、类型注解(可选)、**默认值(必需)**、可写性 |
| 配置字段 | 名称、类型注解(可选)、默认值(运行时只读;**可引用服务资产**,如数据库连接) |
| 实现绑定 | 代码模块 或 子图(内部拓扑 + 外部端口→内部端口的映射) |
| 输入组 | 多个输入组各一一对应一个输出组(方法/返回值);组触发 = Readiness 检查(pending 聚合,策略见 [端口、绑定与输入资格](./graph-ports-bindings.md) §2.4),执行消费 pending;组间参数不互传,状态共享(见 [执行模型](./graph-execution-model.md) §2) |
| 初始化输入 | 可选,至多一组:`__init__`,实例创建时执行一次,可接受参数;初始化完成前方法组不执行;读档不重跑初始化 |
| 输入资格 | **Signal 是输入资格,不是数据端口的默认附着物**:已连接资格槽的端口,Readiness 需 `pending AND level == HIGH`;未连接 = 条件恒成立;level LOW 时数据照常接收缓存,effective = 默认属性(见 [执行模型](./graph-execution-model.md) §3)。**输出侧无隐式信号**:数据节点只产 Data Event;信号节点(声明 signal-out)显式处理信号,可接受数据 |

**不包含任何内部结构**——内部如何维护数据、如何计算,接口上不可见。

函数节点的**输入→输出对应关系是声明的一部分**(编辑器可见,一切显式):哪个输入触发哪个输出写死在类型里,实现只是填空。对应之外的输入不触发任何输出。触发语义详见 [执行模型](./graph-execution-model.md) §2。

## 3. 节点域分类(category,1.3)

每个节点类型声明一个**域分类**,七值严格枚举,声明必填、构造点校验(`NodeType.__post_init__`):

| 值 | 含义 | 内置节点 |
|---|---|---|
| `signal` | 纯信号运算元件(电平组合) | AND / OR / NOT / Latch |
| `data` | 数据节点(方法即转移函数) | Join / Buffer / Switch / Threshold / Comparator / Counter / Random |
| `source` | 自走源节点(每轮自动执行) | Clock / Timer |
| `encapsulation` | 封装节点(封装外部能力) | LlmCall / ContextStore / ContextCompile |
| `host` | 宿主交互节点(编辑器注入/控制台对接) | Input / Output |
| `custom` | 自定义节点(用户自建类型) | 子图 / 脚本节点(编译产物自动 `custom`) |
| `test` | 测试节点(验证系统运行/渲染效果,非基础节点) | MultiGate / Simulate |

设计要点:

- **域与形态正交**:信号节点/自走/子图等形态仍由声明派生(`is_signal_node()` / `is_source()`),category 只回答"哪个域"——两者不重复;
- **内核不解释语义**:值域是严格枚举,但每个值的含义是声明侧约定;编辑器/工具按 category 分组调色板、映射域色,不硬编码节点清单;
- **向后兼容**:枚举引入前的旧资产反序列化缺 category 键 → 兜底 `custom`;显式非法值在构造点拒绝(声明错误立即暴露);
- 脚本节点恒为 `custom`(用户自建类型),脚本无需声明 category。

## 4. 状态与配置:按可写性声明

节点类型的每个字段声明其可写性,这是区分"参数"与"状态"的唯一标准:

- **可写字段(状态)**:运行时可被转移函数更新或被输入信号写入,必须有默认值;属于世界事实,持久化;
- **只读字段(配置)**:编辑期设定,运行时只读;属于图资产,版本化。

关键推论:**"参数可以被信号调制"不需要特殊机制**——时钟的频率就是一个可写状态字段(带默认值),有输入端口写入它。"反向传播影响时钟信号"退化为普通连线,零特例。

## 5. 实现黑盒:代码与子图

- **代码节点**:实现绑定到一个程序模块;内部可以是确定性规则、世界推演、LLM 调用,接口不关心;
- **子图节点(复合节点)**:实现绑定到另一张图(内部拓扑 + 外部端口→内部端口的映射);嵌套深度不限——对上层图而言,它就是一个普通节点实例;
- **脚本节点(1.2)**:实现绑定到内嵌 Python 脚本(`impl.kind="script"`,脚本正文在 `impl.source`)——脚本是声明权威,端口/组/状态/配置从脚本编译生成,行为经方法重载(tick/init/schedule)。完整指南见 [Script 可编程节点](./graph-script-node.md);
- 用户"定义一个节点"的本质 = **带接口声明的封装**(子图或脚本);可视化编辑器 = 图编辑 + 类型编辑,两套界面共用一套资产系统。

## 6. 类型系统:声明可选,鸭子类型兜底

与 Python 语言和解释器保持一致:

1. **声明**:数据端口/状态字段/配置字段/全局变量/常量可带类型注解,不带 = Any;**控制端口无类型**(不承载数据);端口 kind(data/control)是声明中不可省略的部分;
2. **校验**:只在编辑事务提交时做静态检查——两端都声明了类型才查兼容(子类型或 Any 通过),任一端未声明就放行(最多给提示);
3. **运行时**:零强制。数据包载荷就是 Python 对象,节点内部对任意输入自行处理——处理不了不是类型系统的问题,走 [异常策略](./graph-execution-model.md) §7。

## 7. 节点协议是唯一边界

实现节点协议 = 注册为能力,等价于既有文档中 Extension Registry 的接口契约:

- 图运行时只认接口,不认实现;
- 新能力 = 新节点类型资产,不动运行时;
- 多智能体 = 多节点围绕连线与全局变量协同,而非互相调用。

## 8. 协议稳定,实现可迭代

接口的层级足够低——需要长期稳定的只有 Node / Port / Signal / State / Graph / Event / Asset / Snapshot 这少数几个概念。**人格算法、记忆算法、RAG、情绪模型、剧情系统、世界模拟、LLM、Agent、场景生成,全部可以在这个稳定底座之上持续演化。**

以人格节点为例,同一协议下的实现可以自由迭代:

```
V1:固定人格向量 → V2:可学习偏置矩阵 → V3:动态人格矩阵
→ V4:带时间演化的矩阵 → V5:矩阵 + 神经网络
```

只要外部协议(端口、状态、配置)没有改变,上层图**完全不需要知道内部发生了什么**。由此产生两个工程性质:

1. **技术债隔离**:节点内部实现很差,债务被限制在 `[节点接口] → 黑盒内部实现` 内,而不是扩散到整个 Runtime 与所有模块;
2. **同一协议多实现并存**:同一个世界可以同时挂 角色 A = 简单人格节点、角色 B = 偏置矩阵节点、角色 C = LLM 人格节点、角色 D = 用户自定义人格子图——世界规则不需要因此改变;用户可以在编辑器里直接替换实现(如 `Benevolent.v2` → `Ruthless.v1`)。

"某个核心理论还没研究完成,所以项目还不能真正开始"的困境因此消失:**先让引擎运行起来,再逐渐创造更好的节点**——先用固定权重占位,之后替换成真正的矩阵模型,甚至某天发现理论完全错误,也只需要替换对应节点或子图。
